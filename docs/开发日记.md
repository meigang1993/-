### 4. 构建链路风险:未压缩 bundle 的可用边界(细化第 2 条警告)

- **摘要**:为避免后续会话(含容器/协作 AI)误用 AI 协助环境生成的**未压缩 bundle**,明确其可用边界与被拦截的确切环节。**本条为第 2 条中"不可用于发布"的完整依据。**
- **结论(三场景分离)**:

  | 场景 | 未压缩 bundle | 依据 |
  |:--|:--|:--|
  | 浏览器直接打开(本地 `publish/index.html` 或线上部署) | ✅ **可正常运行** | 即普通 JS;11 个文件均已 `node --check` 通过,与 terser 版逻辑等价 |
  | `git commit` | ❌ **被 pre-commit 拦截** | 见下 |
  | 正式发布 | ⚠️ 能跑但**不合规** | 项目规范要求 terser 产物 |

- **被拦截的确切位置**:`.githooks/pre-commit` 第一段即执行 `node tools/build-publish-bundles.js --check`。该模式会把**磁盘上的 bundle** 与 **terser 当场重新压缩的结果**逐字节比对;拼接产物必然不一致,抛 `Stale publish bundles: ...; run npm run build:bundles`,**提交被拒**。
- **体积不是被拦原因(已核实)**:未压缩合计 1.65 MB,压缩版约 1.11 MB,增幅约 +49%。但 `tools/check-asset-budget.js` 的 `singleFile: 2MB` / `criticalTotal: 2MB` 限制对象是 **`publish/assets/` 下的素材**,**不覆盖 `publish/bundles/`**。故 1.65 MB 不违反体积预算,卡点纯粹是 `--check` 的逐字节比对。
- **pre-commit 其余校验(一并注意)**:`--check` 之后依次还有 `check-static.js`、`check-resources.js`、`check-asset-budget.js`、`check-script-contracts.js`;且钩子**前置**要求 `src/original`、`publish` 下**无未暂存的改动、无未跟踪文件**,并校验 `publish/` 路径不含非 ASCII 字符与空格。
- **成因**:AI 协助环境(容器)无法访问 npm registry(403),装不了 `terser`,只能按 `tools/publish-bundles.json` 顺序做等价拼接。**此约束属环境限制,不属源码缺陷**,源码本身无任何问题。
- **行动规则(对后续所有会话/容器 AI)**:
  1. 需要**验证功能** → 可用未压缩 bundle 临时覆盖 `publish/bundles/` + `publish/index.html`,浏览器 `Ctrl+F5` 后实测,**允许**;
  2. 需要**提交或发布** → **必须**由本地执行 `npm run build:bundles` 生成 terser 压缩版,**禁止**把未压缩产物提交入库;
  3. 不得因"浏览器能跑"而误判产物合规——能跑 ≠ 能提交。
- **修改**:`docs/开发日记.md`(本条)
- **提交**:见仓库 `git log`(本次日记提交)。

### 5. 解决:容器环境内重新构建并压缩 bundle(撤除第 2/4 条中的"无法压缩"限制)

- **摘要**:此前判定"AI 协助环境无法压缩,只能出未压缩 bundle"**已不成立**。实测在容器内成功装配 **terser 5.49.0** 并跑通官方构建,产物经 `--check` 逐字节校验通过。**后续会话不应再以"装不了 terser"为由只出拼接产物。**
- **根因与解法**:npm registry 被墙(403)导致 `npm install` 不可用,但 **jsDelivr / unpkg 的 npm CDN 可直连**,可绕过 registry 直接取包文件。
- **可复现步骤(供后续会话/容器 AI 照做)**:
  1. **版本必须取自 `package-lock.json`,不可自选**:本项目锁定 `terser@5.49.0`、`acorn@8.17.0`、`@jridgewell/source-map@0.3.11`、`gen-mapping@0.3.13`、`resolve-uri@3.1.2`、`sourcemap-codec@1.5.5`、`trace-mapping@0.3.31`。版本不符则压缩字节不一致,`--check` 必失败。
  2. 取 terser 预构建 UMD 单文件:`https://cdn.jsdelivr.net/npm/terser@5.49.0/dist/bundle.min.js`,置于 `node_modules/terser/dist/`,并写 `package.json` 令 `main` 指向它。
  3. 用 `https://unpkg.com/<pkg>@<ver>/?meta` 列出包内真实文件,挑 `dist/*.umd.js`(或 `dist/*.js`)下载;terser bundle 的外部依赖只有 `@jridgewell/source-map` 与 `acorn`,前者再递归依赖 gen-mapping / resolve-uri / sourcemap-codec / trace-mapping。脚本见交付包 `tools/fetch_deps.py`。
  4. **构建需 git worktree**:`publish-build-version.js` 会 spawn `git` 校验版本。容器内须先 `git init` 并把**线上旧 bundle** 提交为 HEAD 基线,否则报 `Publish version checks require a Git worktree`。
- **推进版本号的三处(易漏!只改 index.html 会失败)**:
  1. `publish/index.html` 的 `meta[name=game-build]`(10 处 `v=` 一并替换);
  2. `publish/villa.css` 顶部 4 行 `@import url("./villa-*.css?v=<版本>")`;
  3. `publish/index.html` 里 build badge 的**显示文本**,格式为 `v26.0908.01`(与 `20260908-01` 不同,正则 `\\d{8}-\\d+` 匹配不到,**必须单独替换**)。
  以上任一遗漏,`check-script-contracts` 均报 `villa stylesheet imports must match` 或 `visible build badge must match` 并退出码 1。
- **实测结果**:11 个 bundle 全部生成,合计 **1.2 MB**(未压缩为 1.65 MB);`--check` 输出 `Publish bundles are current: ...` 退出码 0;`check-static`、`check-script-contracts` 通过。
- **容器侧局限(仍存在)**:`check-resources`、`check-asset-budget` 在容器内**必失败**,原因是容器只下载了 CSS/bundle、**未下载 `publish/assets/` 素材**(实测补下载缺失素材后 `check-asset-budget` 即转为通过)。**此二者失败与构建产物无关**,本地素材齐全时应正常通过,勿误判为构建缺陷。

### 11. 【待修】实测发现 2 处真实缺陷(原被误判为"容器环境问题")

#### 缺陷 A:解锁弹窗确认按钮在设计分辨率下溢出视口(严重,影响可玩性)

- **现象**:`preview-unlocks.spec.js` › offline defeat event,点击 `[data-first-defeat-complete]` 超时,报 `<nav id="nav" class="nav-list bottom-nav"> intercepts pointer events`。
- **诊断数据**(`1280×720`,即 README 声明的游戏设计分辨率):

  | 元素 | y | height | bottom | 视口 |
  |:--|--:|--:|--:|--:|
  | `.villa-hall` | 109 | 532 | 641 | 720 |
  | `.villa-modal`(fixed) | 109 | 532 | 641 | 720 |
  | `.modal-card.event-modal` | 172 | 597 | **769** | ⚠️ 溢出 49 |
  | `.actions` > `button` | 703 | 43 | **746** | ⚠️ 溢出 26 |

- **相关 CSS**(`publish/villa-modal.css`):

  ```css
  .villa-modal { position: fixed; inset: 0; ... contain: layout paint; }
  .modal-card { max-height: 92%; overflow-y: auto; }

    height: min(92vh, 680px); max-height: 92%; display: flex; flex-direction: column; overflow: hidden;

  .vn-lines { min-height: 0; flex: 1; overflow-y: auto; }
  ```

### 12. 弹窗溢出修复定稿:改用相对容器百分比,移除窄设备分支(方案 A)

承接第 11 条的缺陷 A。用户确认采用方案 A,已完成并提交 `9faaff09da5f`。

#### 根因再厘清(比第 11 条更准确)

诊断 fixed 的**包含块链路**后发现,`.villa-modal` 写的 `position: fixed; inset: 0` **并没有相对视口定位**:

```
.villa-modal      h=532   contain: layout paint + backdrop-filter   → 自身也是 CB
  ↑ 被劫持
.villa-hall       h=532   contain: layout paint                     → 真正的劫持者
  ↑
.panel content-panel h=550 backdrop-filter
  ↑
.game-shell       h=720
```

即 `contain: paint` 让 `.villa-hall` 成为 `.villa-modal` 的包含块,所以 fixed 的"视口"实际只有 532 高。**而弹窗却按 `92vh`(=662) 计算高度**——容器 532 装不下 662,必然溢出。

**结论:`92vh` 这个写法本身是错的**。该弹窗的容器不是视口,不该用 vh 计量。改为相对容器的 `92%` 才是对的方向。

#### 最终修复

```css
/* publish/villa-modal.css */
.modal-card.update-modal, .modal-card.event-modal {
  height: min(92%, 680px);   /* 原为 min(92vh, 680px) */
  max-height: 92%; display: flex; flex-direction: column; overflow: hidden;
}
```

**无条件生效,不区分视口**。

#### 为何移除 `@media (min-height: 600px)`

### 13. hit-bump 消失之谜:是测试构造缺陷,不是代码 bug(缺陷 B 结案)

承接第 11 条缺陷 B。用户追问"hit-bump 去哪里了",已彻底查清并修复测试,提交 `cba52bdd8c9b`。

#### 先说结论

#### 排查过程(排除了两个错误猜想)

**猜想 1:bump 被 700ms timer 提前清除** —— ❌ 排除。

- 测试传入的 `recover() {}` 是空函数,不会清理

1. **战斗 CSS 是按需加载的**,不随页面初始加载:

   ```
   .unit-art  computed: display=block(本应 grid), width=1280px, height=0px
   → getBoundingClientRect().height = 0
   ```

   (真实尺寸 `96×96` 定义在 `battle-units.css:25`,该文件没加载,故 height=0)

3. `battle-float-numbers.js:57` 的 `popOne()` 首部有防御:

   ```js
   const rect = art.getBoundingClientRect();
   if (rect.width <= 0 || rect.height <= 0) return false;   // ← 在这里返回
   ...
   window.BattleBumpFX?.bumpTarget?.(art, float.kind, float.value);  // 第 77 行,永远到不了
   ```

   `rect.height = 0` → 提前 return → **`bumpTarget()` 从未被调用** → `hit-bump` 从未添加。

4. 佐证:诊断脚本记录 4 次 render,每次 `syncBumps()` 前后 `.unit` 的 `hit-bump` **均为 false**,证明 record 从未进入 `active` Map,不是"加了又被删"。

测试补 `startFreshGame(page)`,让 battle CSS 先加载,`.unit-art` 获得 96×96 尺寸:

```diff
+   startFreshGame,

    await openGame(page);

```

### 17. 协作约定:scripts/ 脚本的使用边界与 Git 保存规范

#### 一、scripts/ 五个脚本分成两类,不可混用

**硬性禁止**:

2. **不要把密钥写进命令参数**——已确认脚本当前使用

**B 类 · 可本地执行**

### 18. 模块拆分方案:按职责边界 + 风险,不按行数机械切割

**本节由用户口述指定记录。已逐项核对仓库实况,数据全部吻合
(`src/original/` 实测 407 个 JS,19 个 ≥150 行)。**

#### 核心原则

**不要为了降低行数而增加大量只有几行逻辑的薄文件**——这会扩大加载顺序
和维护成本。拆分必须基于"职责边界 + 风险",而非行数。

#### 优先级与拆分建议

**高优先级**

| 文件 | 行数 | 拆法 | 风险 |
|:--|--:|:--|:--|
| `battle-card-active-relics.js` | **194** | ①主动饰品判定与通用校验 ②各类主动饰品效果 ③兼容门面继续暴露原 API | 卡牌使用、饰品触发、MVP 统计可能共享状态 → 重复触发或漏记一次 |
| `battle-status-cards.js` | **167** | ①状态牌创建/唯一性/手牌归一化 ②状态牌结算/移除/过期 ③精英·BOSS 抵抗判定 | 状态牌贯穿摸牌、伤害、响应、消耗、存档 → 重复移除、错误入弃牌堆、恢复后状态不一致 |
| `store-migrations.js` | **163** | 只留"版本调度 + 迁移编排";具体迁移下沉到已有 `store-migration-characters.js` / `store-migration-runs.js` / `store-migration-normalizers.js` / `store-unlock-migrations.js`,必要时加版本路由或旧存档修复模块 | **迁移拆错比普通 bug 更危险**——直接影响已有玩家存档 |

**中高优先级**

| 文件 | 行数 | 拆法 | 风险 |
|:--|--:|:--|:--|
| `battle-effects.js` | **157** | 只拆"异步效果调度/恢复"或"渲染同步"这类**完整职责**;**禁止**按单个动画函数切碎 | **风险最高**:涉及 runtime.version、state 替换、动画队列、`whenIdle()`、重绘冻结、错误恢复。必须保留**单一 runtime 所有权**,否则旧动画写入新战斗、队列重复 drain、战斗永久锁定 |

**中优先级**

| 文件 | 行数 | 拆法 |
|:--|--:|:--|
| `battle-effect-card-transfers.js` | 159 | 按"抽牌/入手牌"与"弃牌/消耗/跨阵营转移"拆 |
| `cadicis-skills.js` | 163 | 按**技能族**拆(准备阶段 / 主动出牌 / 伤害反应 / AI 选择),不按函数数量拆 |
| `ruins-elite-skills.js` | 162 | 同上 |
| `edis-skills.js` | 159 | 同上 |

> 技能文件风险:同时被战斗流程、AI、UI 提示、恢复流程调用,
> 拆独立文件后易造成 **bundle 顺序错误或循环依赖**。
> **只在下次功能修改触及它们时顺带拆分**,避免无收益的大范围重构。

**暂不建议主动拆分**(核心编排器,拆分会增加全局 API / 初始化顺序 /
异步上下文传递复杂度)

```
runtime-loader.js              170 行
battle.js                      153 行
battle-combat.js               150 行
store-main-save-scheduler.js   154 行
battle-action-selection.js     155 行
```

除非新增功能明确形成独立职责,否则不动。

#### 已有依赖必须沿用,禁止复制

`battle-status-card-registry.js`(109 行)**已经承担**部分状态牌判定职责,
拆分 `battle-status-cards.js` 时应继续沿用,**不要再复制一套状态牌判定**。

#### 六条主要风险(拆分时必须逐条对照)

1. **Classic Script 加载顺序** —— 新文件必须写入 `tools/publish-bundles.json`
   且**放在父门面之前**;忘记注册会导致构建或运行时缺少全局对象。
2. **兼容门面 API 变化** —— 外部依赖全局对象和原函数名。拆分后的门面
   **只能组装、委托、导出**,不得趁机改变参数、返回值或同步/异步行为。
3. **闭包依赖丢失** —— 项目大量使用 `window.Xxx = deps => {}`。拆分时明确
   传递 `state` / `battle` / `render` / `actionGuard` / `waitEffects` / `record`
   等依赖,避免辅助模块偷偷读取过多全局变量。
4. **异步状态过期** —— 战斗动画、保存队列、敌方 AI、技能恢复都可能跨
   Promise 或计时器。**必须保留** `state` / `battle` / `generation` /
   `actor` / `phase` 的捕获和二次校验,不能因"只是重构"而删掉这些检查。
5. **副作用顺序改变** —— 例如先写存档还是先清理 marker、先推进游标还是先
   触发提示、先完成动画还是先结算奖励。这类变化**不会**立刻表现为语法错误,
   但会造成重复奖励、卡死或恢复错误。
6. **构建和缓存版本** —— 拆分会改变 generated bundle,需重新生成对应 bundle
   并同步递增 `game-build` 及相关 CSS/loader 版本,否则旧新脚本混用。

#### 每次拆分后必须同步更新

```
docs/original/architecture.md
docs/original/game-settings.md
tools/publish-bundles.json
```

#### 每次拆分的验收标准

- 父门面 **API 不变**
- 辅助模块 **无新增公开 API**
- **bundle 顺序明确**
- **只跑直接相关 QA**(不盲目全量)

#### 推荐实施顺序

```
1. battle-card-active-relics.js   ← 异步风险最低,先做边界整理
2. battle-status-cards.js         ← 补状态牌专项验证
3. store-migrations.js            ← 重点验证旧存档迁移
4. battle-effects.js + battle-effect-card-transfers.js
5. 技能文件                        ← 下次功能改到它时顺带拆
```

### ⚠️ 修正 ⑦：不是 preloadAssets 失败，而是 GameBundles.load 挂起

§21 推测"preloadAssets 返回失败列表 → throw → 换皮中止"。
实测**推翻该推测**，铁证如下（对 `GameBundles.load` 与 `GameAssets.preloadAssets`
同时打桩，3 秒超时竞速）：

    loadCalls    : ["battle"]
    loadResult   : "ERR TIMEOUT_3S after 3002ms"
    preloadCalls : 0                      ← 关键
    stateSkin    : "lokar_default"
    appearanceSaving : false

`preloadCalls = 0` 说明 **`preloadAssets` 根本没有被调用**，
流程卡在更早的 `await window.GameBundles.load("battle", ...)`，
该调用在容器内 3 秒未返回。

因此换皮中止点不是 §21 推测的第二处（`preloadAssets` throw），
而是第一处 `GameBundles.load` 长期 pending。
`button.disabled = true` 之后因其他 render 重建 DOM 而复原为 false，
这也解释了为什么"按钮看起来可点、但状态从未改变"。

**仍需本地确认**：`GameBundles.load("battle")` 在本地是否同样挂起。
若本地瞬时返回，则属容器素材/网络缺失；若本地同样超时，则是真缺陷。

### 补充 ⑤：副本地图是倒序渲染，滚动为渐进平滑动画

查明地图布局（`.tower-map` 内 `.map-layer` 的 DOM 顺序与视口 y）：

    DOM index 0  → n10-0   y = -456（最顶层）
    DOM index 7  → n3-0
    DOM index 8  → n2-0    y =  424
    DOM index 9  → n1-0    y =  534（最底层，玩家起点）

即**第 10 层渲染在最上方、第 1 层在最下方**（塔由下往上爬）。
`.tower-map` scrollHeight 1122 / clientHeight 470，scrollTop 已达最大值 652。

关键时序差异（同一场景不同等待时长实测）：

    等待 1200ms → n2-0 视口 y = 1078（视口外，点击落空）
    等待 2000ms → n2-0 视口 y =  424（视口内，可点）
                  n1-0 视口 y =  534（当前层，可见）

**结论**：地图存在渐进式平滑滚动，最终会滚到当前层且当前层与下一层均可见。
§21 担心的"进入副本应自动滚动到当前层"的**产品体验问题不成立** ——
稳定后当前层 `n1-0` 确实在视口内。
失败纯粹是测试在滚动动画完成前取 `boundingBox()` 坐标并用
`page.mouse` 点击（Playwright 的 mouse API 不自动滚动）导致落空。
定性为测试时序问题，非产品缺陷。
