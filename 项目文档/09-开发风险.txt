===============================================================
  魅魔杀 - 开发风险与防御措施
  交接对象：DeepSeek 重制
===============================================================

【一、异步战斗中旧请求覆盖新状态】

风险：旧的动画、预加载、AI等待、定时器或promise在状态被替换后
仍然提交到新的战斗或状态。

防御措施：
1. 在异步边界前捕获状态、战斗对象、角色、阶段和运行时generation
2. 在每次提交、重渲染、解锁或继续前再次验证
3. 加载、离开或替换战斗时使旧队列和定时器失效
4. 敌人思考和 autoEnemy 保持单一所有权
5. 使用请求ID防止旧请求覆盖新结果

示例：
  let latestRequestId = 0;
  async function refresh() {
    const reqId = ++latestRequestId;
    const result = await someAsyncOperation();
    if (reqId !== latestRequestId) return; // 已被新请求取代
    applyResult(result);
  }

【二、Rerender破坏DOM和动画】

风险：同一画面重渲染导致立绘闪烁、视频/动画重启、滚动位置偏移
或旧DOM索引应用到另一个角色的手牌。

防御措施：
1. 保留匹配的图片/视频节点和稳定key的角色卡
2. 从 visualHp 派生HP相关的技能状态立绘和装饰器
3. 将持久卡牌美术渲染为可重用的图片节点并异步解码
4. 不在队伍/测试选择器中使用延迟 content-visibility
5. 保留模态、手牌、公共轨迹和日志滚动，除非新内容需要跟随
6. 从字段白名单重建持久悬赏任务并转义所有存储的文本
7. 处理手牌前验证手牌所有者uid
8. 在异步手牌重排序中保留选中卡牌对象身份
9. 控件在隐藏提示未交互前保持可见锁定

【三、多段攻击重复结算】

风险：多段攻击重复扣费用、重复伤害、重复发牌或重复触发技能。

防御措施：
1. 多段攻击每一段都必须拥有独立continuation
2. 处理中断时先推进步骤游标，恢复时只执行未完成步骤
3. 不得重复扣费用、重复应用伤害、重复发牌或重复触发技能
4. 退出战斗必须使旧输入和旧异步结果失效
5. 准备序列在调用可能打开提示的钩子前推进步骤游标
6. 嵌套的敌人准备游标在外层准备完成时清除
7. 结束阶段技能消耗每回合计数器前必须声明当前回合

高风险例子：半魅魔血、多段攻击、全目标攻击、反击、准备伤害、
结束阶段技能和敌人AI继续。

【四、存档失败被当作空档】

风险：存档失败被误认为"没有存档"，或新游戏覆盖销毁恢复数据。

防御措施：
1. 区分空数据和读取失败
2. 通过实际SDK完成序列化写入
3. 浏览器 dzmm.kv 成功为权威结果，localStorage 仅 best-effort
4. 启动不依赖 dzmm.fn
5. 按 _saveVersion 然后 updatedAt 选择有效副本，KV平局时云端赢
6. 验证大小、结构、资源、收据和迁移后才替换有效副本
7. 持久化物理卡牌为规范身份+花色，拒绝未知身份
8. 手动槽、主存档、设置和生命周期队列所有权分离
9. 返回真实部分/失败状态并保留明确重试路径

【五、牌库数量混淆】

风险：牌库物理数量和唯一名称数量混淆，导致显示错误。

防御措施：
1. 实体卡总数统计永久实体数量，包括重复牌
2. 图鉴进度统计唯一正式牌名
3. 公共牌库分组显示 持有xN
4. 战斗牌堆总数包含摸牌堆、弃牌堆、消耗堆及同侧所有手牌
5. 跨阵营偷牌时显示数量转移到持有者一侧

【六、虚拟牌重复计数】

风险：虚拟牌重复计入MVP或重复触发角色技能。

防御措施：
1. 虚拟牌和响应牌保持独立
2. 一张玩家可见卡牌或技能激活算一次卡牌使用
3. 内部虚拟牌使用 skipMvpCardCount 不重复计数
4. 军令状通过其生成的虚拟【魔王军入侵】只计一次

【七、动画兼容性】

风险：缺失或损坏的Web Animation API阻止结算或输入。

防御措施：
1. 支持缺失的 Element.animate()、animation.finished 和 Array.prototype.at()
2. 在配置持续时间后应用最终帧并释放
3. 用fallback截止时间限制浏览器动画完成等待
4. 在拒绝的动画工作后恢复控件和效果队列

【八、持续表现成本】

风险：永久transform、filter、opacity或border动画在已解码战斗立绘上
强制持续合成并降低刷新率。

防御措施：
1. 标准待机战斗立绘保持静态
2. 专属皮肤待机循环限制在所选皮肤层
3. 在减少动态下禁用
4. 对称或视觉不变的装饰器保持静态
5. 保留其他立绘移动、滤镜、装饰器运动和碰撞给有界的入场、技能、
   受击、状态、胜利或结算反馈
6. 合并重复受击到活跃短碰撞而不是重新启动

【九、音频问题】

风险：暂停的AudioContext上调度音效消失，旧BGM请求误报失败，
零音量音效仍分配音频图。

防御措施：
1. 等待 AudioContext.resume() 并确认运行状态
2. 排队延迟解锁音效而不是丢弃
3. 源或音量变化时使旧BGM播放/淡入工作失效
4. 仅在敌人选择后预备最终任务或遭遇BGM
5. 避免在不透明origin iframe中进行CORS敏感的fetch预加载
6. 零SFX音量下不分配合成效果节点

【十、媒体与路径】

风险：玩家文本绑定到img/audio/video src导致大量无效请求；
无效文件名破坏发布。

防御措施：
1. 只为已验证的媒体数据创建媒体元素
2. 消耗战斗预加载失败，渲染明确的立绘/卡牌fallback
3. 保留可见重试操作
4. 使用条件DOM创建，不是CSS隐藏
5. publish/ 下所有路径ASCII-only且无空格
6. 使用相对运行时资源路径

【十一、Bundle与模块漂移】

风险：源码变更未到达生成的bundle，依赖顺序变化，或逻辑回到compatibility facade。

防御措施：
1. 所有未压缩模块在源码目录，只通过生成bundle发布
2. 源码变更后重新生成受影响bundle
3. 当publish/包含其他JS或提交的bundle与当前源码不同时失败检查
4. 版本化启动和延迟脚本URL以及样式表URL
5. 保持依赖顺序
6. facade仅限装配、委托和导出

【十二、小视口裁切】

风险：固定最小画布尺寸或文档级滚动在小窗口中裁切控件并移动整个游戏壳。

防御措施：
1. html/body/.game-shell 适配当前动态视口，无固定最小宽高
2. 文档滚动元素固定，根应用safe-area padding
3. 保留组件级内部滚动
4. flex和grid滚动owner设 min-height: 0
5. 保持1280x720基线无文档溢出

【十三、运行时错误边界】

风险：分离的promise拒绝或未捕获的回调异常在第一个交互帧后发生，
留下操作守卫、控件、加载视图或非提示战斗锁定。

防御措施：
1. 记录并保留标准化的source、code、message和stack
2. 重置应用和战斗操作守卫及其DOM锁
3. 在解锁前推进运行时generation
4. 正常战斗退出丢弃排队的旧输入
5. 清除瞬态开始、出征、测试战斗、素材重试和中断加载状态
6. 通过一个共享helper分类每个可见战斗提示
7. 回滚中断的战前副本节点
8. 恢复战斗效果表现
9. 错误对话框作为全局模态栈的最后一个子元素，陷阱焦点
10. 提供玩家触发的重试，不重放旧工作
11. 不通过 dzmm.loading.error() 报告启动后失败

【十四、确定性随机性】

风险：直接熵调用、比较器排序或视觉随机改变游戏结果。

防御措施：
1. 所有游戏随机性通过 GameRandom 消耗 state.random.seed + cursor
2. 迁移为旧存档创建状态一次
3. 所有洗牌使用共享Fisher-Yates实现
4. 持久run和task ID从持久seed/cursor派生，不推进游戏随机
5. 动画ID、确认ID、对话变体和音频噪声使用瞬态随机流

【十五、中断战斗链】

风险：由伤害、反击、分享或状态处理打开的提示重新开始整个动作，
跳过剩余命中/目标/阶段，或恢复错误的敌人。

防御措施：
1. 暂停确切的未完成反应步骤
2. 保留命中索引、目标索引、来源、角色、阶段和待处理队列
3. 只在所有必需的提示和反应完成后恢复
4. 重新检查来源存活、活跃角色、阶段所有权和结算锁
5. 动画后技能奖励在同步链触发前捕获第一个直接命中结果
6. 将continuation失败传播到拥有动作边界
7. 从失败恢复后不持久化稳定操作checkpoint
8. 不重跑已完成的目标选择、响应或伤害修改器

【十六、存档与云端协调】

风险：旧写入覆盖更新进度，失败云端读取显示为空，
新游戏覆盖销毁恢复数据，或生命周期删除误报成功。

防御措施：
1. 区分空数据和读取失败
2. 按key通过实际SDK完成序列化写入
3. 浏览器KV成功为权威，localStorage为best-effort
4. 启动不依赖dzmm.fn
5. 按 _saveVersion 然后 updatedAt 选择有效副本
6. 验证大小、结构、资源、收据和迁移
7. 持久化物理卡牌为规范身份+花色
8. 手动槽、主存档、设置和生命周期队列分离
9. 返回真实部分/失败状态

【十七、结算与经济】

风险：重复奖励、零值fallback、重排恢复动作或对错误物品的库存操作。

防御措施：
1. 需要有效奖励payload或从权威收据/增量恢复
2. 保持不确定结算待处理且可重试
3. 使用幂等有序收据/高水位标记
4. 保持动作顺序，在未解决的早期动作后阻止后续动作
5. 按稳定物品身份+收据识别库存操作
6. 按显示权威序列、卡牌身份和槽位索引识别商店购买
7. 仅通过core初始化和刷新商店库存
8. 在收费或清除奖励前预检容量
9. LocalCore操作返回明确的changed/accepted/apply结果
10. 更改检测和不相关动作不序列化/克隆/重建完整库存

【十八、SDK调用死循环】

风险：代码自己把请求打成死循环，每帧狂调，烧积分、撞限流429。

防御措施：
1. 贵接口（completions/draw/fn.invoke）绝不放进：
   - requestAnimationFrame / 游戏主循环
   - setInterval / setTimeout 轮询
   - pointermove / scroll / oninput / resize 回调
   - 响应式watcher
   - 自触发回调
2. 需要周期性时用自调度setTimeout（上一次返回后才安排下一次）
3. 玩家输入触发的贵调用要debounce
4. 游戏循环与网络解耦：主循环只读内存状态
5. fn.invoke默认只调用一次，不包重试循环
6. 连续失败熔断（连错N次就停）
7. 限流不会替你兜死循环，降频是你的责任
